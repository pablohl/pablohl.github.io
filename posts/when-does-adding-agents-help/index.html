When does adding agents help?

What one paper found about teams of AI agents—and what its results give us a reason to test.

A reading of Kim et al., Capable language models can outgrow the benefits of collaboration.

My view · executive summary

Start with a capable single-agent baseline. I would test a team against a specific failure, then ask whether the improvement justifies its cost.

  • Divide the work when separate research could recover missing evidence.
  • Measure the trade-off: correctness, actual token use, tool charges and time.
  • Test checking: compare a separate reviewer with the single agent checking its own work.

These are comparisons to evaluate, not a default architecture to adopt. Read my proposed tests ↓

01 / The question

Would a team do this task better?

An AI assistant can search for information, use tools and keep working until it has an answer. Instead of giving all that work to one assistant, you could run several: ask them to work on different parts, check each other’s answers or report to a coordinator.

Here, an agent is a language model working through a task with tools. A team runs several such workers; its architecture defines their roles and how they communicate.

The paper compares one agent with four kinds of teams on six benchmarks. We’ll examine the tasks, results and extra work before considering what to test next.

02 / The tasks

What were the agents asked to do?

The study covers 260 combinations of model, benchmark and architecture, using models from OpenAI, Google and Anthropic. These are the study’s models, not a list of current recommendations.

03 / The results

Teams helped on some tasks and hurt on others.

For each of the six benchmarks, the study tests one single-agent baseline and four team architectures: centralized, decentralized, independent and hybrid. Start with the overview of all four teams, then inspect one architecture at a time in the chart below.

Independent
Workers do not exchange messages; their outputs are combined afterward.
Centralized
A coordinator assigns work, reviews reports and combines the answer.
Decentralized
Workers share and discuss findings with each other before selecting an answer.
Hybrid
A coordinator directs work, and workers can also exchange findings.

The possible splits do not predict a winner on their own: Finance Agent and BrowseComp-Plus both involve multiple sources, yet their gains differ. Use the buttons below to compare the same team arrangement across all six benchmarks.

Why might Finance Agent and PlanCraft differ?

The same centralized architecture improves the Finance Agent mean and lowers the PlanCraft mean. The paper’s examples suggest a possible explanation: what can proceed separately, and what must wait.

This makes division of work a question to test, rather than a property to infer from a benchmark name. To understand when those handoffs help, we also need to account for the extra work they introduce.

04 / The extra work

How much extra work did the teams do?

The success rates leave out the reporting, discussion and checking used to finish. In the 180 configurations with full cost tracking, teams took more reasoning turns on average. A turn is an execution step, not a fixed number of tokens or seconds. The common budget ceiling is a maximum; runs can finish before using it all.

These averages show extra activity, not a 3.8× or 6.2× token bill. To establish a product cost, measure actual token use, tool charges and elapsed time alongside success. Parallel work may shorten a run while increasing total usage.

Extra work is worthwhile only if it improves the result. That leads to the comparisons I would run next, including whether review catches mistakes.

05 / My view · proposed next tests

What would I test because of these findings?

I would use these findings to choose a comparison, not a default architecture. The tests below ask whether division of work or checking produces a useful gain at an acceptable cost.

1

Test a useful division of work.

If development examples show missing evidence, assign distinct research questions and have workers return sources and findings to a coordinator. Compare with one agent on fresh, predefined tasks. Check whether additional evidence improves the answer; vary the division within the same task set to investigate why.

2

Measure the improvement and its price together.

Keep the total budget ceiling aligned and record success, actual tokens, tool charges and time. Set worthwhile gains and acceptable cost and delay in advance. If you raise the team’s allowance, also test one agent with the larger budget.

3

Compare a reviewer with a self-check.

Compare a separate reviewer with a single agent checking its own work, using the same evidence, criteria and total ceiling. A coordinator can review reports and peers can challenge findings, but agreement alone does not establish correctness. Evaluate what changed and whether it improved the final task result.

My proposed evaluation / not reported study outcomes

What changed during checking?

Save the answer before and after review. Judge both against the same sources, task criteria or tests.

Before reviewAfter reviewWhat to record
IncorrectCorrectA correction. Verify the change and that it survives into the final answer.
IncorrectIncorrectAn unresolved error. Was it missed, accepted, or unsuccessfully corrected?
CorrectIncorrectA new error. Inspect the change and why it was accepted.
CorrectCorrectA correct result retained. Record the extra work; agreement is not a correction.

Use the same scoring unit before and after review. Track new errors as well as fixes, then check task completion: a correct recipe still has to produce the PlanCraft target item. Paper: verification and error propagation ↗

Keep coordination when its measured benefit meets your requirements. Establish that benefit on representative held-out tasks, with repeated runs and uncertainty estimates, and include actual cost and time. The paper justifies trying these comparisons; it does not settle their outcome for your system. If the gain is insufficient, improve or retain the single-agent baseline.
